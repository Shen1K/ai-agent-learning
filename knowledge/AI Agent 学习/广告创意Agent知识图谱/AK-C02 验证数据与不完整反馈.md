# 验证数据与不完整反馈

本案例保留当时的任务条件和发现，不随以后规则变化改写成新案例。原始JSON和执行报告统一从 [[AK-S01 来源与证据登记]] 进入。

## 当时的任务与问题

教学题要求标题不超过18个Python字符并包含咖啡杯，正文不编造商品事实、不说教。模型输出位置的示例为标题“给自己一口空闲”，正文“消息还在闪，先捧起桌边的咖啡杯。”。

程序结果required_headline_term=false正确指出标题缺词，但如果只把布尔值交给改稿模型，没有规则和关键词，它不能可靠地知道怎样修改。学习者主动指出了这一信息缺口。

## 实际数据处理

| 原始记录 | 保留内容 | 处理 |
|---|---|---|
| raw-01 | 本题范围内合格文案 | 保留 |
| raw-02 | 标题缺词 | 保留失败，不补词 |
| raw-03 | 无依据的保温十二小时 | 保留失败，不删承诺 |
| raw-04 | 你必须学会关爱自己 | 保留语义反例 |
| raw-05 | raw-01重复副本 | 去重并记录关联 |
| raw-06 | 无原任务资料 | 隔离待补，不判好坏 |

结果是1条生成评测题和4条评审器校准题，不是4个独立brief。全部是已公开开发／验证材料，不能包装成保留测试集。程序对四条候选检查结果与教学硬标签一致，不代表模型准确率。

## 结果怎样成为可用反馈

存档可以保留case_id与规则编号，通过关联还原条件。改稿输入则需要展开：

- 检查字段：headline。
- 要求：标题含完整字符串咖啡杯。
- 实际标题：给自己一口空闲。
- 违约依据：标题缺词，正文含词不能替代。
- 修改边界：只改标题，保持18字符以内，正文保留。
- 其他有效约束：商品事实与品牌语气仍要传入。

这只是反馈契约示例，未接入真实模型改稿。不能根据缺词直接断言模型忽略了指令，还需排查实际上下文及后处理。

## 如何复核

运行原构建脚本会输出到新的目录，不能覆盖原报告；核对输入文件没有预期标签。若下一步比较真实生成方案，应另外保存模型输入、原始输出和评审版本，不把现成四条候选冒充新模型生成。
