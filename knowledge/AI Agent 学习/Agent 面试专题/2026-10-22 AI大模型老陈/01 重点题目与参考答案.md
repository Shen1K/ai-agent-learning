# AI大模型老陈相关重点题目与参考答案

面向 Agent 应用开发岗位，按架构复用价值、故障影响和追问深度排序。下文把博主提出或讨论的主题重新组织成面试题，参考答案是核验后编写的设计回答。来源编号和主题覆盖统计见[博主内容分析](<00 博主内容分析.md>)；不把这些设计说成学习者已经完成的项目经历。

## 1 什么时候需要 Agent

来源：[S2](https://www.xiaohongshu.com/explore/6ab48a53000000001802e188)、[S4 第 1 题](https://www.xiaohongshu.com/explore/6a9a8cb8000000001203f908)。主题覆盖 2 篇。

**考察意图。** 能否根据任务的不确定性分配控制权，并解释增加自主决策的收益和代价。

**参考回答。** 我会先明确交付结果、可用信息、允许采取的行动和失败后果。已知步骤可以覆盖需求时，用固定流程；单次模型调用加必要检索足够时，就保留这个基线。如果下一步要根据运行中得到的信息决定，且路径难以穷举，再引入 Agent。在实际系统中，可以让模型决定搜索什么或采用哪份资料，由程序固定权限检查、预算和交付确认。

**因果推导。** 固定流程把路径选择留给程序，因而容易复现；开放任务需要处理事前未知的分支，模型决策提供适应性，同时引入额外成本和不确定性。因此要比较任务效果，再决定增加多少自由度。[架构依据](https://www.anthropic.com/research/building-effective-agents)。

**例子。** 对广告 brief 按固定字段检查，可以采用流程；根据资料缺口选择检索来源并调整研究方向，可以采用受约束的 Agent。发布广告属于另一项需要明确授权的行动。

**追问。** 用了 LangGraph 就一定是 Agent 吗？不一定，图里也可以全是固定步骤。RAG 与 Agent 是否二选一？不是，检索可以是固定环节，也可以是 Agent 选择调用的工具。

## 2 工具执行失败后如何恢复

来源：[S1](https://www.xiaohongshu.com/explore/6ad9d0030000000032014ee8)、[S2](https://www.xiaohongshu.com/explore/6ab48a53000000001802e188)。主题覆盖 2 篇；幂等和副作用核验是参考答案补充。

**考察意图。** 是否能区分模型决策错误与外部服务故障，避免恢复操作再次扩大问题。

**参考回答。** 我会让工具返回程序可判断的错误类别。参数错误应先修正参数；权限不足要停止相关行动；短暂的网络或限流错误，在总时限和次数预算内退避重试；长期不可用时选择经过授权的替代方案或明确失败。对会修改外部状态的操作，超时后先查询结果或使用幂等键，不能把没有收到响应当作没有执行。恢复时保留已确认的状态和调用记录。

**因果推导。** 重复相同参数不能修复参数错误；权限不会因为重试而增加；瞬时故障可能恢复；而响应超时只说明客户端没等到结果。错误类别不同，下一步自然不同。[AWS 对超时、重试和幂等的解释](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)。

**验证。** 在模拟工具中分别制造参数错误、限流、无权限和执行后丢失响应，检查是否选择了正确分支，以及是否发生重复写入。

**追问。** 模型能否自行决定无限重试？不能，总预算由程序约束。已经写入外部系统后能否简单回退？需要业务支持补偿或撤销；恢复到旧对话状态不会撤销外部副作用。

## 3 如何评估 Agent 并证明优化有效

来源：[S1](https://www.xiaohongshu.com/explore/6ad9d0030000000032014ee8)、[S2](https://www.xiaohongshu.com/explore/6ab48a53000000001802e188)、[S4 第 10 题](https://www.xiaohongshu.com/explore/6a9a8cb8000000001203f908)。主题覆盖 3 篇。

**考察意图。** 是否知道成功如何定义，能否区分真实改善、随机波动和指标被投机满足。

**参考回答。** 我会先建立有明确成功标准的任务集，覆盖常规任务、失败恢复和边界情况。首先看最终结果是否完成任务、是否满足关键约束，再记录成本、延迟、调用次数和错误类型。比较版本时固定任务与环境，记录模型、提示和工具版本，并做重复运行。根据执行轨迹定位问题，改动后同时检查目标指标和其他指标是否退化。

**因果推导。** Agent 的多步执行会改变环境状态，所以一句“完成了”不能证明结果存在；模型输出有波动，一次成功也不能证明稳定。任务集、重复运行和结果核验共同提供可比较的证据。[Agent 评测的一手说明](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

**例子。** 创意任务的事实和格式可以程序检查，创意质量应使用清晰评分标准并有人校准。调用减少但遗漏 brief 要求，不能算优化成功。

**追问。** Few-shot 应放在哪里？要先区分是给被测 Agent 的示例，还是给评分模型校准标准的示例；两者都要避免泄漏测试答案。调用次数减半，成本就减半吗？不一定，每次输入输出长度、模型、缓存和工具价格都会影响成本。

## 4 如何管理上下文与长短期记忆

来源：[S2](https://www.xiaohongshu.com/explore/6ab48a53000000001802e188)、[S4 第 6 至 8 题](https://www.xiaohongshu.com/explore/6a9a8cb8000000001203f908)、[S7](https://www.xiaohongshu.com/explore/6a6723ec000000000f017d7f)。主题覆盖 3 篇。

**考察意图。** 是否能在有限窗口中保留任务所需状态，而不是把全部聊天记录不断追加。

**参考回答。** 我会把明确的目标、约束、完成状态和待确认项存为结构化任务状态；把冗长原始结果放在外部，保留可引用位置；每轮只选择必要历史、相关资料和工具结果。需要跨会话保留的信息要设置写入条件、来源、有效期和访问范围。接近预算时先压缩冗余，再摘要或检索回读，同时为输出和后续调用留出空间。

**因果推导。** 上下文既有容量限制，也存在无关信息干扰；摘要会丢细节，检索可能漏信息，长期记忆还可能保存过期或错误内容。因此状态、原始证据和摘要应承担不同职责。[上下文管理依据](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。

**验证。** 使用长对话、用户修改要求、摘要后追问细节、相互冲突的历史信息等案例，检查关键约束能否保留，以及是否会把旧决定当成新决定。

**追问。** 长期记忆必须使用向量数据库吗？不必，稳定偏好和明确业务状态可以用普通数据库或文件，语义检索只是读取方式之一。摘要能否替代原始证据？不能，重要事实要能回溯来源。

## 5 权限与人工确认怎样进入执行链

来源：[S1](https://www.xiaohongshu.com/explore/6ad9d0030000000032014ee8)、[S4 第 2 及 5 题](https://www.xiaohongshu.com/explore/6a9a8cb8000000001203f908)、[S5 的 CodeAct 图](https://www.xiaohongshu.com/explore/6a58e4a1000000000f02b03a)。主题覆盖 3 篇。

**考察意图。** 是否理解“模型建议行动”与“系统允许行动”之间必须有可执行的控制。

**参考回答。** 我会按任务提供必要工具，由执行层检查身份、资源范围、参数和操作权限；对高影响行动绑定明确确认。执行代码时限制文件、网络和资源范围。外部文档与工具返回作为数据处理，不能据此扩充权限。日志记录行动与授权依据，便于确认发生了什么。

**因果推导。** 模型生成的调用参数仍可能错误，外部内容也可能包含诱导指令。权限检查需要在实际产生副作用的位置生效，才能避免仅靠文字约定。MCP 的工具规范也把人类控制和客户端检查列为重要设计要求。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。

**例子。** 创意 Agent 可以生成提案草稿；提交到客户工作区时，要确认目标、版本和操作范围。确认后内容发生实质变化，应重新判断授权是否仍覆盖。

**追问。** 每次只读查询都必须弹窗吗？可以依据既有授权和策略执行，不能把确认设计成无差别打断。工具标注只读就能放心吗？标注也是服务提供的数据，仍需信任和实现核验。

## 6 MCP 解决什么问题

来源：[S4 第 3 题](https://www.xiaohongshu.com/explore/6a9a8cb8000000001203f908)、[S6](https://www.xiaohongshu.com/explore/6a4ca8c80000000011004ca8)。主题覆盖 2 篇。

**考察意图。** 能否区分组件职责，以及协议统一了什么、没有决定什么。

**参考回答。** MCP 提供客户端与服务端之间的标准上下文交换方式，包括能力发现和工具等能力的使用。Agent 的宿主仍负责模型调用、工具选择后的执行策略、状态和授权。Skills 包装任务方法和资源，可以指导 Agent 使用 MCP 工具。Function Calling 是模型表达工具请求的接口机制；MCP 是应用与服务交换能力和结果的协议，它们可以配合。

**因果推导。** 统一接入方式减少应用分别适配每个工具服务的工作；协议连通并不自动决定任务计划、结果正确性或权限策略。[MCP 架构](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)，[Skills 标准](https://agentskills.io/home)。

**追问。** SSE 与 Streamable HTTP 如何比较？应区分旧版 HTTP+SSE 传输和新版 Streamable HTTP；后者仍可使用 SSE 返回流。按 2025-11-25 规范，标准传输为 stdio 和 Streamable HTTP。[传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。协议调用成功等于业务成功吗？不等于，还要读取工具结果、业务错误与最终状态。

## 7 如何比较 Agent 模式

来源：[S5](https://www.xiaohongshu.com/explore/6a58e4a1000000000f02b03a)。主题覆盖 1 篇。

**考察意图。** 是否知道每种机制引入什么能力，以及如何判断额外复杂度值得。

**参考回答。** 我会按实际问题选择机制：运行中需根据结果决定下一步时，用行动与反馈循环；动作适合用程序组合时，考虑代码执行；需要动态补资料时，引入自主检索；有清晰评分标准时，考虑评估与修订；存在可独立分工的任务时，再考虑多 Agent。它们可以组合，选型需要比较任务效果、耗时、成本和恢复难度。

**因果推导。** 各机制解决的问题不同，因此不存在统一的复杂度升级路线。CodeAct 统一了可执行动作的表达，但执行环境仍需受控；反思增加了反馈机会，但如果没有可靠纠错信号，也可能把正确内容改坏。[CodeAct 原论文](https://arxiv.org/abs/2402.01030)，[自我纠错的条件与局限](https://arxiv.org/abs/2310.01798)。

**追问。** 多 Agent 为什么可能更慢？协调、重复检索和结果整合会增加开销，依赖强的任务也难并行。如何证明自我反思有用？在相同任务集上比较启用与禁用，并检查纠错和改坏两种情况。

## 8 KV cache 与 Prefix caching 为什么有效

来源：[S4 第 9 及 11 题](https://www.xiaohongshu.com/explore/6a9a8cb8000000001203f908)。主题覆盖 1 篇。

**考察意图。** 是否能从因果注意力机制推导缓存复用，并区分存储、计算和性能收益。

**参考回答。** 对常见因果 Transformer，历史位置不能看到后来加入的 token，所以在相同前缀和模型条件下，历史位置的各层 K、V 可以复用。生成新 token 时计算当前 Q、K、V，让当前 Q 读取历史和当前 K、V，不需要重新计算旧位置的 Q。Prefix caching 进一步在请求共享相同前缀时复用已有缓存，减少共享部分的预填充。

**因果推导。** 后续 token 需要查询历史位置的信息，因此复用 K、V；旧 Q 对应的是旧位置的查询，生成当前位置时不再需要。KV 来自各层 Attention，但为重新得到这些 KV 而需要执行的前缀 FFN 等计算也会被一并跳过，不能据存储格式推导仅优化 Attention。[KV 原理](https://huggingface.co/docs/transformers/main/cache_explanation)，[Prefix caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)。

**追问。** 缓存会让新 token 不再读取历史吗？不会，当前查询仍要访问可见历史的 K、V。为什么输出很长时前缀缓存收益有限？它主要节省 prefill，后续生成仍须逐步计算，长输出可能让 decode 成为主要耗时。

这道题涉及推理原理，应在理解应用执行链后展开；目标岗位包含推理服务或性能优化时，再提高其准备优先级。
