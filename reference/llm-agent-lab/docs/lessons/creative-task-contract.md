# 商品创意项目第一课 事实约束与创意方案

本课从一张虚构商品海报开始，学习怎样把商品资料、用户需求和模型创意分开，再组合为可执行任务。核心是确定哪些内容允许模型提出，哪些内容必须从约定的数据源取得。业务由教师准备，不要求先掌握广告行业知识。

配套材料：[商品与任务示例](<../../lessons/creative_studio/lesson01_fixture.json>)。商品、品牌、价格和规则均为教学假设，不代表真实企业制度或广告法规。

## 本次任务

用户要求：“为这款杯子做一张秋日居家主题海报，突出温暖的感觉，展示活动价。”

本课先制作一张1024×1024的草稿。三种场景、多轮修改和批量生成留到后续。这里只定义生成前的任务，不投放、不发布，也不评价点击率或转化率。

| 商品字段 | 教学资料中的值 |
|---|---|
| 商品编号 | cup-001 |
| 品牌与名称 | 暖序，暖序陶瓷咖啡杯 |
| 材质与容量 | 陶瓷，350 mL |
| 颜色 | 米白色 |
| 活动价 | 69元 |
| 商品图片 | 尚未准备，不能把示意图冒充真实商品素材 |

品牌要求是温暖、简洁。资料未提供保温时长、优惠幅度或销量，所以不能新增这些商品事实。名称与编号帮助选择数据，数据版本帮助以后解释“当时为什么用了这个价格”。

## 为什么先整理任务

直接把“画一张秋日促销海报”交给模型，会把画面创意与商品事实混在一起。即使构图好看，价格错误或多出一个未经确认的功能，仍不满足任务。

我们把输入分成三类。商品资料提供事实，品牌规则和用户要求给出约束，模型在这些边界内提出创意。语言模型输出先作为候选，不自动成为商品资料或新的业务规则。

本课的“任务契约”就是程序各部分共同遵守的输入、输出和检查约定；不是法律合同，也不是一种新模型。使用JSON只是为了把字段分开，让程序容易读取，并不自动保证内容正确。

## 分工与一个完整方案

| 信息 | 本例由谁提供 | 原因 |
|---|---|---|
| 商品名、活动价 | 程序读取商品资料 | 已经有确定数据，不需要重新创作 |
| 图片尺寸、方案数量 | 程序读取明确任务设置 | 便于生成和验收使用同一约定 |
| 标题、场景、背景描述 | 语言模型提出候选 | 需要在约束内组织表达与创意 |
| 商品外观 | 后续使用经确认的固定素材 | 不能让背景生成顺便重画商品 |
| 最终是否接受 | 明确规则检查加必要的人工审核 | 字段有效不等于视觉效果或语义一定正确 |

一个教师编写的候选方案是：标题“把秋日暖意，留在这一刻”，背景为暖色窗光和木质桌面，中央预留商品位置。背景不绘制商品、文字或价格；后续由程序叠加固定商品素材与文字层。这是本项目的可控制作方案，并非所有海报系统都必须这样实现，也不保证生成模型总能遵守提示。

下面仅展示最终文字层的结构：

```json
{
  "brand": "暖序",
  "product_name": "暖序陶瓷咖啡杯",
  "headline": "把秋日暖意，留在这一刻",
  "price_text": "活动价 ¥69"
}
```

其中`headline`来自创意候选，其余商品信息来自资料和固定格式。模型不必生成整个对象；程序可以把不同来源的字段组合起来。价格来源与标题来源不同，后续出现错误时才能准确定位。

## 什么能检查 什么仍需审核

程序可检查尺寸、必填字段和文字层价格是否与资料一致。创意候选若写“保温24小时”，资料不支持这项功能，就需要拒绝或修订该候选；不能靠文字格式正确或模型自评分高放行。

自由文案是否暗示未经确认的性能，以及画面是否协调，不能仅靠字段类型检查完整解决。后续再加入有明确标准的人工审核和视觉模型辅助，不宣称本课已有通用语义校验。

配套JSON是教师准备的例子，没有自动调用模型或完成图片生成。`reference_image_path`为`null`，表示缺少商品图片，因此`status`为`blocked_missing_product_asset`。结构化任务可以准备，但此时不能宣称完整海报已制作完成。

## 运行最小任务组装程序

[任务组装代码](<../../lessons/creative_studio/task_contract.py>)实现“读取→检查约定→组装草案→输出状态”，只用Python标准库。直接运行下面的命令，不必先切换到项目目录，也不需要安装新依赖：

```bash
python3 ./lessons/creative_studio/task_contract.py
```

它会依次展示原始资料和缺价格变体。变体只修改内存副本，不改写源JSON；原始69元价格仍保留。示例中新增`request.show_activity_price=true`，把显示价格要求明确交给程序，不依赖程序猜测自然语言需求。

| 函数 | 职责 | 重点阅读 |
|---|---|---|
| `load_fixture` | 读取JSON为字典 | JSON的null对应Python的None；文件读取失败不是价格缺失 |
| `validate_contract` | 检查本课使用的字段、编号和固定策略 | 字段值为null是合法缺失；字段拼错、价格类型错误是交接错误 |
| `assemble_task` | 从不同来源组装一个新任务草案 | 商品名与价格来自商品资料；只从候选中选取创意字段 |
| `main` | 串联步骤，展示两个案例 | deepcopy复制嵌套数据，避免缺价实验污染原始资料 |

优先阅读`assemble_task`里的价格分支。`if price is None`判断“是否未提供”，而不是“数值是否为零”；`blocking_issues.append(...)`将原因加入列表。后面的图片检查独立执行，所以同时缺两项会保留两条原因，不会只报告第一项。

## 实际对照结果

| 输入 | 价格文字 | 阻塞原因 | 状态 |
|---|---|---|---|
| 原始69元资料 | 活动价 ¥69 | 缺商品图片 | needs_input，待补充 |
| 仅把价格改为null | null，不填价格 | 缺活动价、缺商品图片 | needs_input，待补充 |

两个案例都保留标题候选，但都不能生成成品。有价格只说明这一项有依据，不代表任务已满足全部要求。

如果价格存在、指定素材文件也存在，程序返回`needs_review`，表示待审核，不是已可渲染。当前只检查文件存在，不验证图片格式、商品对应关系或授权；标题是否暗示未经证实的性能也仍待审核，因此`can_render`始终为false。当前没有审核通过和图片生成步骤，不应为得到一个成功状态而手动把这个值改成true。

旧示例JSON中的`execution_plan`是之前的教师示范快照，代码故意不读取它，而是每次根据输入重新组装。否则缺价格后复用旧方案，就可能把历史69元误用成本次价格。

[16项测试](<../../tests/test_creative_task_contract.py>)覆盖缺价与缺图同时报告、零值、两位小数、错误类型／负值／非有限数、编号不符、候选不能覆盖事实、旧方案不复用、输入不变以及素材文件检查。测试中现存文件是临时占位文件，只用于检查存在性分支，不是已准备好的商品图片。

在项目根目录运行测试：

```bash
python3 -m unittest discover -s tests -p 'test_creative_task_contract.py' -v
```

这部分是普通程序的数据边界，不涉及模型训练或自动模型调用。后续再接入创意模型，模型输出也必须遵守同一分工。实际学习证据与下一动作仍见学习进度（本分享版未收录）。
