# 创意项目第二步 优惠规则与文案审核

本课把业务规则、文案中的价格主张和程序计算分开。目标不是让模型决定优惠制度，而是让已确认的规则成为审核依据，并保留理解错误、规则缺失和计算不符的不同处理路径。

## 本课规则

[规则文件](<../../lessons/creative_studio/promotion_rules_v1.json>)为教师制定的虚构规则，活动编号autumn-demo、版本1，不代表真实商家的制度。

- 商品为cup-001，每杯69元。
- 商品金额满99元减10元，包含恰好99元。
- 运费不计入门槛，但计入最终支付总额。
- 每单最多一张券，不叠加其他优惠。
- 本课只核算该单一商品，假定处于活动有效期且用户持有可用券。库存、退款、活动日期校验及多商品分摊不在范围内。

金额使用整数分：69元存为6900，99元存为9900。原第一课商品资料不改动；这份规则独立用于优惠审核示范，尚未接入第一课组装入口。后续集成需解决商品价格和活动规则的来源对应及版本管理。

## 各步骤的责任

1. 业务规则和订单情境由教师准备，代表系统应独立取得的业务资料。
2. 文案理解把自由文字映射为数量、价格口径、声称总价和是否声称已用券。
3. 程序从规则和订单重新计算门槛金额、优惠额及总价，不接受候选自报的正确答案。
4. 比较已识别的主张，输出冲突、条件性一致或待确认；不能直接发布海报。

本课的[文案理解快照](<../../lessons/creative_studio/promotion_cases.json>)是教师编写的示例，程序只重放，不调用模型、不自动理解新标题。接入真实模型后需要另行评测漏提取、误提取和条件理解错误，不能用核算测试代替模型评测。

例如“买两个杯子，领券后共128元（免运费）”被示范性整理为：

```json
{
  "quote": "买两个杯子，领券后共128元（免运费）",
  "quantity": 2,
  "price_basis": "order_total_including_shipping",
  "claimed_total_cents": 12800,
  "claims_coupon_applied": true
}
```

price_basis明确比较的是含运费的整单总价，而不是每杯价格；quote用于回到原文。引用存在不证明其他字段理解正确。本课只核算指定订单主张，没有自动覆盖全文全部事实和条件。

## 实际案例结果

| 文案或资料情况 | 规则核算 | 处理 |
|---|---|---|
| 单杯免运费，声称券后59元 | 商品69元，未达门槛，实付69元 | 按当前理解存在冲突，复核语义后退回 |
| 两杯免运费，声称券后共128元 | 138−10=128元 | 按当前理解一致，继续其他审核 |
| 单杯加30元运费，声称券后共89元 | 门槛金额仍69元，优惠0元，实付99元 | 按当前理解存在冲突，复核语义后退回 |
| “组合优惠，每杯低至59元” | 未明确组合及整单金额口径 | 待确认，不能直接拿59与订单总价比较 |
| 运费是否计入门槛的规则为null | 不作核算 | 待补规则，不能默认false或true |

needs_information表示缺规则；needs_confirmation表示需要明确含义、修正输入或核对版本。consistent_given_interpretation表示“如果这份文案理解正确，则该价格主张与计算一致”，不是海报审核通过。所有结果can_publish均为false。

## 阅读与运行

[审核代码](<../../lessons/creative_studio/promotion_review.py>)只用Python标准库，包含详细注释。从main看流程，再阅读review_case和calculate_order，最后看coupon_discount。

```bash
python3 ./lessons/creative_studio/promotion_review.py
```

运行会打印规则版本、每个标题、文案理解快照、中间计算和处理状态。最后只在内存中把运费规则改为null作对照，不修改规则文件。脚本不生成图片，不发布，不调用外部接口。

三个关键函数分别处理不同难点：

- coupon_discount判断参与金额是否达到门槛，用>=而非>。
- calculate_order确定哪些金额参与门槛，再计算实付金额。
- review_case核对活动／规则版本、引用和候选结构，再比较主张与计算。

## 验证范围与已知限制

[13项测试](<../../tests/test_promotion_review.py>)覆盖门槛前后、运费口径、两杯总价、缺失规则、版本错配、假引用、数量错配、非法金额及输入不变。98.99／99／99.01是门槛函数测试输入，不假装固定69元杯子能组成任意金额订单。预期结果按本课规则手算写入，属于教学验证，不是独立业务负责人验收。

特别保留一个反例：原文说一个杯子，但快照错误地解释为两个，并配上两杯订单。程序可能得到consistent_given_interpretation，因为它不会独立理解原文。这说明“计算正确”和“理解正确”需要分别验证；引用存在也不能排除理解错误。当前程序不声称独立完成全文语义审核。

在项目根目录运行课堂测试：

```bash
python3 -m unittest discover -s tests -p 'test_promotion_review.py' -v
```

与[第一课任务组装](<creative-task-contract.md>)的联系是：资料先按约定准备，审核再检查具体主张；图片缺失与其他审核事项仍不能跳过。动态断点和本人证据见学习进度（本分享版未收录）。

## 用DeepSeek替换理解快照

[真实调用入口](<../../lessons/creative_studio/deepseek_review.py>)新增了独立接口，不改原离线示范。程序从当前终端环境变量DEEPSEEK_API_KEY取密钥，仅放在官方HTTPS请求的认证头中，不写入代码、提示或文件。用户终端设置的变量不会自动传入助手的另一个执行环境。

默认只预览，不联网：

```bash
python3 -S ./lessons/creative_studio/deepseek_review.py
```

在已经配置密钥的同一个终端，加--live发送一次真实请求，可能计费：

```bash
python3 -S ./lessons/creative_studio/deepseek_review.py --live
```

-S跳过Python的site及第三方包初始化，不清除环境变量。本脚本只用标准库，因此不需要这部分初始化。此次测试遇到本机Anaconda初始化时的ASCII解码错误，使用-S完成验证；没有修复或改动Python安装。不要把-S当作依赖第三方包脚本的通用解决方案。

默认只测one_cup；可用--case two_cups选择另一条。每次--live最多发送一次请求，输出最多512 tokens，不自动重试。超时或断连不证明服务端没有处理／计费，重试前应先判断原因。脚本不打印认证头或服务端原始错误正文，不关闭证书验证，也不跟随HTTP重定向。

调用分为五段：

1. 打印模型输入：提取要求和待审标题；不含参考快照、业务正确价格或密钥。
2. 请求DeepSeek。任务是提取原文声称的内容，不是替文案纠错。
3. 检查完成状态及JSON结构后，显示模型理解；空回复、截断、假引用、非法类型等停止处理。
4. 用本次理解替换内存副本里的旧快照，交给原review_case核算。
5. 显示提示版本、请求的模型、耗时与返回的token用量；不自行推算账单金额。

此步骤先实现模型的语义提取职责，还不是让模型独立完成所有业务规则审查。价格口径含糊时允许返回null／unclear并转确认。模型输出JSON合法并不证明语义正确，仍保留条件性一致状态及can_publish=false。

2026-10-07核对[DeepSeek官方Chat Completions文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)后，入口默认使用deepseek-flash、关闭思考模式、JSON输出、temperature=0和max_tokens=512。这些设置是本课基线，不是已验证的最优配置；temperature=0也不承诺多次输出绝对相同。可用--model明确指定服务支持的其他模型，不能把不存在的模型名当作已支持。

[12项接口测试](<../../tests/test_deepseek_review.py>)使用假响应和假密钥，覆盖请求不泄漏标准答案、预览不联网、单次调用、快照替换、输出校验、错误隐藏及禁止重定向。这些离线测试与旧65项共77项通过，但不代表真实密钥已验证、网络连通或模型提取准确。实际结果需由用户执行--live后查看，日志反馈只需模型理解与审核结果，不要发送密钥。
